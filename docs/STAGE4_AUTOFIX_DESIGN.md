## 0. 왜 이 문서인가 — 기능이 아니라 **주장 자격**의 전제다

지금 `"토큰 N% 절감"` 을 못 쓴다. 이유가 둘이고, 엄밀함과 무관한 사실이다.

1. 우리 코드는 고객 에이전트를 **건드리지 않는다.**
2. 고객이 고쳤어도 **그 절감을 우리가 못 잰다** (전후 비교 없음).

★ **같은 컴포넌트가 둘을 동시에 해결한다.** 고치는 자리에 앉은 것만이 *"내가 무엇을 막았는지"* 를 셀 수 있다. 억제한 호출은 **관측된 반사실**이다 — 막지 않았으면 일어났을 일을 우리가 안다. 그래서 Stage 4 의 산출물은 수정 기능이 아니라 **계측된 절감액**이고, 그게 주장을 사실로 바꾼다.

## 1. 현재 구조의 사실 (grep 검증, 2026-10-07)

| 컴포넌트 | 하는 일 | 요청 경로? |
|---|---|---|
| `live.py` | 트레이스 **파일을 폴링** (매 폴마다 처음부터 재독) | ✗ 밖 |
| `capture.py` | LangGraph 실행 후 **OTel span export** 후처리 | ✗ 밖 |
| `submit.py` / `ingest/*` | 파일 → Trace → 리포트 | ✗ 밖 |

**요청 경로에 끼는 컴포넌트 0개** (`proxy|middleware|intercept|def wrap|monkeypatch` 전수 검색: 무관한 2건뿐 — 테스트 주석, 비유적 "proxy").

⇒ 🔴 **고치려면 새 위치가 필요하다. 기존 코드 재배치로는 안 된다.** 이것이 Stage 4 가 Stage 1~3 의 연장이 아닌 이유다.

## 2. 무엇을 고칠 수 있나 — 디텍터마다 다르다

| detector | 찾는 것 | 자동수정 | 위험 | 자리 |
|---|---|---|---|---|
| `redundant_read` | 같은 `target` 재독 | **캐시에서 서브** | 낮음 (읽기는 멱등) | 도구 호출 경계 |
| `repeat`/cascade | 동일 도구 출력 반복 | **중복 호출 억제** | 낮음 (읽기인 경우) | 도구 호출 경계 |
| `duplicate_creation` | 같은 엔티티 재생성 | 억제 | **높음 — 부작용 호출** | 도구 호출 경계 |
| `context_resend` | 같은 청크 재전송 | 청크 제거 | **높음 — 에이전트 판단이 바뀐다** | 메시지 조립 경계 |

★ 핵심 분기: **위 둘은 읽기(idempotent)라서 안전하고, 아래 둘은 손대면 결과가 바뀐다.**
`context_resend` 가 금액은 가장 크지만(이 코퍼스에서 낭비의 거의 전부) **대화의 본질**이라 자르면 동작이 변한다. Phase 1 에서 제외한다 — 금액을 따라가면 가장 위험한 것부터 건드리게 된다.

## 3. 어디에 앉는가 — 후보 셋

| | 위치 | 장점 | 단점 |
|---|---|---|---|
| **(가)** | **도구 실행 래퍼** (SDK/런타임 레벨) | 모델 응답에 손 안 댐 ⇒ **동작 변화 위험 최소** · 억제 계측이 자연스럽다 | 런타임마다 어댑터 필요 |
| (나) | LLM API 프록시 | 모든 런타임 공통 | 프롬프트를 바꿔야 효과가 난다 ⇒ **판단이 바뀐다** · **원본이 우리 서버를 지난다** (기존 금지 문면과 충돌) |
| (다) | 파일 감시 + 사후 제안 (현행 연장) | 새 위험 0 | **고치지 않는다 ⇒ 절감 주장 불가** |

**추천: (가).** (나)는 프라이버시 문면과 정면 충돌하고 동작 변화 위험이 (가)보다 크다. (다)는 지금 상태이고 이 문서의 목적을 달성하지 못한다.

## 4. 측정 — 이것이 실제 산출물

래퍼는 억제할 때마다 **단위와 모집단을 이름에 담아** 기록한다 (2026-10-07 결함의 직접 교훈):

- `suppressed_tool_calls_count` — 억제한 **도구 호출 건수**
- `cache_miss_count` — 분모
- `cache_invalidation_events` / `cache_entries_dropped_count` — 안전 기본값이 얼마나 일하는지 (**단위가 둘이라 필드도 둘**: 발동 횟수 ≠ 버린 엔트리 수)
- `not_cacheable_count` — 게이트가 손대지 않은 호출 수
- `suppression_window` — 세션 1개 / 프로젝트 / 기간 (**모집단 명시**)

★ 이것으로 `"이 고객은 N일간 도구 호출 X건을 안 돌렸다"` 가 **계측값**이 된다.

### 🔴 토큰·달러 필드는 Phase 1 에서 **삭제됐다** (2026-10-08 정정)

초안은 `suppressed_input_tokens`("억제로 모델 입력에 안 들어간 토큰 수")와
`suppressed_cost_usd` 를 뒀다. **둘 다 성립하지 않는다.**

근거는 디텍터 자신의 비용 모델이다 — `detect/redundant_read.py:9`:
`waste tokens = tokens(cand.output_text)` 를 **다음 턴 LLM 입력 요율**로 매긴다.
즉 재독의 낭비는 *그 출력이 대화에 두 번째로 들어가 이후 모든 턴에서 입력으로
실려 나가는 것*이다. 그런데 P1.4 에서 우리는 (B) 를 택해 **캐시된 내용을 그대로
에이전트에 돌려준다** — 그러면 그 내용은 대화에 그대로 남고 **입력 토큰은 여전히
실려 나간다.** 아껴진 것은 **도구 실행뿐**이다.

🔴 **P1.4(B) 와 초안 §4 는 동시에 참일 수 없었다.** 에이전트가 내용을 받았다면
토큰은 안 줄고, 토큰이 줄었다면 에이전트가 그 내용을 못 받은 것이다.

⇒ 토큰을 실제로 줄이려면 **도구가 준 것보다 짧은 것을 돌려줘야** 하고, 그건 모델이
보는 것을 바꾸는 일 = **Phase 3 (context 축소)** 이고 별도 사전등록 대상이다.

| Phase 1 이후 | |
|---|---|
| 쓸 수 있다 | "이 세션은 도구 호출 N건을 덜 돌렸다" |
| 🔴 쓸 수 없다 | "토큰 N 절감" · "$N 절감" · "N% 감소" |

★ **§0 의 전제가 Phase 1 으로는 달성되지 않는다.** `"토큰 N% 절감"` 주장 자격을
여는 것은 Phase 1 이 아니라 **Phase 3** 이다. §0 은 "같은 컴포넌트가 둘을 동시에
해결한다" 고 적었는데, 정확히는 **같은 자리(도구 호출 경계)가 둘을 해결할 수 있지만
Phase 1 의 동작(내용 그대로 서브)으로는 토큰 축이 안 열린다.**

### 정확성 가드 (절감보다 우선)
캐시가 틀린 값을 주면 절감이 아니라 버그다.
- 세션 스코프 + TTL
- **쓰기/부작용 도구 감지 시 해당 target 무효화**
- `is_error` 응답은 캐시 금지 (기존 §29.2 tool-error gate 와 같은 원칙)
- 🔴 **정확성 실패 시 기본값은 "무효화"(안전) — 절감 숫자를 위해 유지하지 않는다**

# Phase 1 코드 수준 설계 (LangGraph · `redundant_read` · 안전 기본값)

## P1.1 붙을 자리 — `BaseTool.invoke` / `ainvoke`

확인됨 (`langchain_core` 1.4.7):
`BaseTool.invoke(input, config=None, **kwargs)` · `ainvoke` 동일 · `name` 은 모델 필드.

고객 API 는 **한 줄**이다. 그게 이 단계의 제품 요구사항이다.

```python
from clew.autofix import ToolCache

cache = ToolCache()
tools = cache.wrap(tools)          # ← 이 한 줄
app = builder.compile()
app.invoke(inputs)

cache.report()                      # 억제 계측
```

`ToolCache` 를 모듈 전역이 아니라 **객체**로 둔다: 계측의 모집단(= 이 객체의 수명)이 이름으로 드러나야 하고, 한 프로세스에 여러 그래프가 있을 때 섞이면 안 된다 (결정 ④).

래퍼는 `name` · 스키마 · 설명을 **그대로 보존**한다. 모델이 보는 도구 목록이 달라지면 안 된다 — 그 순간 동작 변화다.

## P1.2 캐시 키 = **디텍터의 키 그대로**

```
key = (tool.name, _extract_target(input_text))
```

`clew.detect.redundant_read._extract_target` 를 **재사용한다**(복제하지 않는다). 이유는 `cascade.confirm_pair` 를 live 와 batch 가 공유하는 것과 같다 — **고친 것과 잰 것이 같은 규칙이어야** "우리가 막은 것" 이 "우리가 센 것" 과 일치한다. 키 함수를 두 벌 두면 둘이 우연히만 일치한다.

캐시하지 않는 경우 (디텍터가 세지 않는 것과 동일):
- `target` 이 `None`
- 도구가 `_READ_TOOLS`(= `_IDEMPOTENT_TOOLS − _NON_READ_IDEMPOTENT`)에 없음

## P1.3 무효화 = **디텍터의 interval gate 그대로** (결정 ②)

`find_redundant_reads` 는 두 읽기 사이에 ① 같은 target 쓰기 ② shell 도구가 있으면 **세지 않는다.** 억제기는 같은 조건에서 **캐시를 버린다.**

| 사건 | 조치 |
|---|---|
| `_WRITE_TOOLS` 호출, target T | **T 무효화** |
| `_SHELL_TOOLS` 호출 (`Bash` 등) | 🔴 **전체 무효화** — payload 가 불투명해 무엇이 바뀌었는지 모른다 |
| 응답이 `is_error` | **캐시 금지** (기존 §29.2 tool-error gate 와 같은 원칙) |
| 판정 불가 | **무효화** (결정 ②) |

Phase 1 스코프 = `ToolCache` 객체 수명(= 보통 한 세션). 지속 캐시는 Phase 2.

## P1.4 🔴 억제된 호출도 **span 을 남긴다**

억제했을 때 두 선택이 있고, **하나는 우리 제품을 망가뜨린다.**

- (A) span 을 남기지 않는다 → 트레이스가 깨끗해지고 **우리 리포트가 "낭비 없음" 을 찍는다.** 고객이 보는 가치 증거가 사라진다.
- (B) span 을 남기고 `clew.suppressed = True` 를 붙인다 → 트레이스가 **에이전트가 하려던 것**에 충실하고, 억제가 기록으로 남는다.

**(B) 를 택한다.** 억제는 **관측된 반사실**이고(§0), 그 기록이 절감액의 근거다. (A) 를 택하면 성공할수록 리포트가 비어 보인다 — 0.5.1 에서 `Total waste $1.665249` 바로 아래 `no waste detected` 가 찍혔던 것과 같은 종류의 자기부정이다.

suppressed span 은 **캐시된 내용을 output 으로 싣는다.** 에이전트는 실제로 그 내용을 받았으므로 그게 사실이다.

### ✅ 구현됨 (2026-10-13) — 붙이는 방법은 실측으로 정해졌다

P1.7 이 열어둔 *"`ToolCache` 를 OTel span 에 어떻게 붙이나 — `capture.py` 경로와 사용자
자체 계측 둘 다에서"* 가 닫혔다. **답은 tracer 를 아예 안 잡는 것이다.**

억제된 호출을 조기 반환하지 않고 **`BaseTool.run()` 으로 되돌려 보낸다.** 그러면 호출자가
이미 돌리고 있는 계측이 그 호출에 대한 tool span 을 평소대로 만들고, 그 span 의 output 이
캐시된 내용이 된다. 우리는 provider 도 tracer 도 만들지 않으므로 `capture.py` 의 로컬
provider 와 사용자 전역 provider 에서 같은 코드가 돈다.

실측 (2026-10-13, `LangChainInstrumentor` + `InMemorySpanExporter`, 동일 입력 2회):

| | 실제 도구 실행 | tool span |
|---|---:|---:|
| 수정 전 | 1 | **1** |
| 수정 후 | 1 | **2** |

`ToolCacheReport` 의 카운터는 양쪽 동일하다 — span 이 늘었을 뿐 세는 값은 안 건드린다.

🔴 **마커는 `_run` 안에서 못 단다.** 같은 날 실측: 거기서 `trace.get_current_span()` 은
`NonRecordingSpan` 이고 context 가 무효라 `set_attribute` 가 무음 no-op 이다. 계측기가
콜백으로 span 을 만들고 그것을 current 로 세우지 않기 때문이다. 그래서 `clew.suppressed`
는 **context metadata**(`openinference.instrumentation.using_metadata`)로 실어 보낸다 —
그 경로는 span 에 실제로 도달한다.

⚠️ **아직 아무도 그 표시를 읽지 않는다.** `ingest/*` 는 Phase 1 범위 밖(§1)이라, 억제가
걸린 트레이스를 리포트에 넣으면 그 반복은 여전히 낭비로 계산된다 — **그건 사실이다.
에이전트는 실제로 두 번 물었다.** "찾아서 막았다" 와 "찾았는데 계속 일어난다" 를 가르는
것이 이 표시를 지금 쓰는 이유다.

## P1.5 계측 필드 (결정 ④)

필드명에 **단위**를, 표시에 **모집단**을 담는다.

```
suppressed_tool_calls_count     억제한 도구 호출 건수
suppressed_input_tokens         모델 입력에 안 들어간 토큰 수
suppressed_cost_usd             위를 실제 티어 요율로 환산한 금액  ← §8 게이트
cache_serve_count               분자
cache_miss_count                분모
cache_invalidation_count        무효화 발동 횟수 (안전 기본값이 얼마나 일하는지)
suppression_window              모집단 (ToolCache 수명 · 세션 id · 기간)
```

표시 순서 — **숫자 크게 먼저, 모집단은 아래**:

```
      18 tool calls avoided
      124,000 tokens
   ─────────────────────────
   this session · 3 files · 2 invalidations
```

## P1.6 🔴 Phase 1 은 **건수만 낸다** (2026-10-08 정정)

초안은 "출하 범위 = 건수 + 토큰까지, 달러는 결함 수정 후" 였다. **토큰도 빠진다** —
이유는 요율 결함이 아니라 **토큰이 애초에 안 줄기 때문**이다(§4 정정 참조).
캐시가 내용을 그대로 돌려주므로 그 내용은 대화에 남고 입력으로 계속 실린다.

⇒ **Phase 1 출하 범위 = 억제 건수 + 캐시 계측(미스·무효화·비대상).**
달러는 두 겹으로 잠겨 있다: ① 토큰 축이 Phase 3 이고 ② 요율 결함 2건 미수정(§8).
고객 체감("같은 파일 네 번 → 한 번")은 **건수만으로 선다.**
